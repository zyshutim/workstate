# Workstate 产品需求文档

相关文档：[文档入口](README.md) · [技术方案](TECHNICAL_DESIGN.md) · [实现状态](IMPLEMENTATION_STATUS.md)

## 1. 产品定义

Workstate 是用户与 Agent 之间的本地共享工作记忆。

线性会话只能记录“当时说了什么”，无法稳定表达项目之间的关系、项目内部的并行工作、长期认知、短期计划、历史变化和待讨论问题。Workstate 将不同 Coder、模型和会话产生的工作证据重新组织为可持续维护的项目状态，让用户和任何 Agent 都能直接接手工作。

Workstate 同时服务两类读者：

- 用户：看清项目正在发生什么，重新接手工作，找到历史决定和原始证据。
- Agent：读取准确的项目认知、当前计划和相关历史，无需用户重新解释。

## 2. 核心问题

### 2.1 会话是线性的，工作不是

一个会话中可能交替推进多个项目和任务；一个项目也可能分布在多个会话、模型和客户端中。会话本身不能成为项目结构。

### 2.2 长期认知会在压缩和换会话后丢失

项目是什么、核心对象如何定义、已经确认过哪些原则，需要成为独立于任何模型会话的正式项目认知。

### 2.3 离开项目后难以重新接手

用户真正需要的是停在哪里、剩下什么、正在等待什么、下一步如何继续。按日历生成的固定日报不能准确适配实际工作节奏。

### 2.4 历史结论难以找回

重要决定可能只是某轮对话中的一句话。用户需要从项目认知、工作概要、议题、工作历史和原始对话中统一检索，并回到准确证据。

## 3. 产品目标

1. 建立跨会话、跨模型、跨客户端的项目记忆。
2. 让用户在离开项目一段时间后快速恢复工作上下文。
3. 让 Agent 通过统一上下文直接接手项目。
4. 保留非线性工作中的主线、并行、切换、完成和回归过程。
5. 将项目认知、工作概要、项目议题、工作历史和原始证据明确分层。
6. 持续沉淀用户与 Agent 的 Persona、协作规则和工作 Loop。

## 4. 产品原则

- 原始会话是证据来源，不直接等同于项目结构。
- 项目认知只保存长期成立的项目事实、对象关系、原则和边界。
- 工作概要只保存当前接手所需的短期状态和执行计划。
- 议题保存尚未进入执行计划的项目问题、方向和想法。
- 工作历史保存已经发生的变化及其顺序、分支和证据。
- 用户决定产品方向；Owner 负责整理、维护和提出修改，不替用户作决定。
- 待确认内容不能成为正式事实。
- 所有自动归属和 Agent 接收方必须可见，不允许静默切换。
- 界面只展示当前任务需要的信息，详细证据按需展开。

## 5. 信息模型

### 5.1 项目认知

项目认知是一份长期、正式、可版本化的项目文档，回答：

- 项目是什么，为什么存在。
- 核心对象分别是什么。
- 对象之间是什么关系。
- 已确认的原则、边界和禁止方向是什么。
- 当前成立的最终结论是什么。

首次认知由用户手动生成并确认成为 `v1`。后续 Owner 只能提出划除、插入、拆分或合并形式的修改。用户可以接受、编辑后接受、拒绝并添加批注。

项目认知在新客户端中采用块式文档：

- 每个认知块拥有稳定身份，可以单独编辑、插入、删除和调整顺序。
- 批注附着在具体认知块或修改上，不成为正式正文。
- Owner 提出的修改直接显示在原文中，以划除、插入和替换方式审阅。
- 未确认修改与正式版本同时可见，但不会覆盖正式内容。
- 阅读状态保持完整文档；进入编辑时只激活当前认知块，避免整页进入一个大输入框。

项目认知不保存普通进度、下一步、待办或短期状态。

### 5.2 项目工作概要

项目工作概要是项目的短期接手与执行状态，替代按日生成的“日报”和独立的“短期 Plan”。

初始规则：项目出现有效工作后，连续 2 小时没有新动作，由该项目的持久 Project Owner 生成一份新概要。没有有效进展时不生成。

工作概要固定只有三个部分：

- 已完成：这个工作周期内已经得到结果的事项。
- 正在进行：当前仍在推进、等待决定或等待验证的事项。
- 待处理：已经确认需要继续处理，但尚未开始的事项。

待办、待确认修改和等待验证事项都进入这三个状态，不再形成独立区域。没有已确认的待处理事项时，Owner 可以给出一条“建议下一步”，但必须明确标记为建议，不能自动成为正式计划。

新概要成为当前接手入口；旧概要保留在工作概要合集和历史中。概要不按自然日强制切割，也不因数小时内的短暂离开重复生成。

### 5.3 项目议题

议题属于项目，保存尚未进入工作概要的内容：

- 还未决定是否推进的方向。
- 需要继续讨论的问题。
- 项目灵感和未来可能事项。
- 已完成处理但仍需等待长期结果的观察项。

议题确认推进后进入工作概要的“待处理”状态或形成新工作线；取消后保留处理结果，不进入执行状态。

### 5.4 工作历史

工作历史保存项目实际发生的变化：

- 主线推进。
- 并行工作和分支。
- 完成与合流。
- 任务切换和恢复。
- 项目、模块、交互和信息架构的认知转折。
- 实现、检查、真实渲染、用户接受、集成和发布状态。

工作历史按时间和语义工作线组织，不按聊天数量或固定时间块机械切分。

### 5.5 原始证据

项目认知、概要、计划、议题和历史节点都必须能回到原始证据。

原始对话使用聊天气泡展示：

- 时间顺序为最旧在上、最新在下。
- 用户消息位于右侧，Agent 消息位于左侧。
- 默认打开并滚动到最新相关消息。
- 向上滚动按需加载更早内容。
- 保留时间、会话来源和关联项目，但不让元数据打断阅读。

## 6. App 信息架构

Workstate 采用标准 macOS App 作为主要产品界面，保留三层结构。

```text
L1 项目空间
  -> L2 项目页面
       -> L3 具体内容详情与证据
```

### 6.1 L1：项目空间

L1 保留自由项目图谱，展示项目状态和项目之间的关系。

固定入口：

- 左下角：工作概要合集。
- 右上角 Navbar：全局搜索、Persona / 协作习惯。
- 右下角：全局 Agent 对话。

#### 工作概要合集

点击左下角入口打开左侧 Sidebar：

- 展示所有项目的最新工作概要。
- 新概要优先显示，并提供未读状态。
- 支持按项目查看历史概要。
- 点击概要进入对应项目的 L2 看板。

工作概要合集承担跨项目进展汇总，不再单独生成一份与项目概要重复的全局日报正文。

#### Persona

Persona 页面用于查看和维护：

- 用户 Persona。
- Agent Persona。
- 协作规则。
- 工作 Loop。
- 禁止行为。
- 规则证据和版本历史。

Persona Collaborator 同时作为全局 Agent 对话中的固定接收方，不局限于 Persona 页面。

#### 全局搜索

全局搜索覆盖：

- 项目认知正文和历史版本。
- 项目工作概要。
- 项目议题。
- 工作历史、分支和转折点。
- 已确认决定和禁止方向。
- 原始对话证据。

搜索结果显示所属项目、内容类型、时间和相关片段，并打开对应 L2 或 L3。入口位于 L1 Navbar，并支持 `Command-K`。

### 6.2 L2：项目页面

每个项目固定包含三个页面。

#### 看板

看板是项目重新接手与执行管理入口，只包含两个主要区域：

1. 当前项目工作概要。
2. 项目议题。

待办、待确认修改和等待验证事项均显示在工作概要内，通过状态和图标区分，不再重复显示为独立模块。
其中待确认认知修改在看板中只显示状态与入口；完整划改、批注和确认操作仍在项目认知页完成。

#### 项目认知

以完整的块式文档编辑器展示正式认知、版本、待确认修改、批注和证据。页面默认完整展开，点击认知块进入编辑；Owner 修改以行内对比显示，不混入项目进度。

#### 工作历史

提供时间视图和分支视图：

- 主线始终连续。
- 真实并行任务从前一节点分出，在后续节点合回。
- 单一任务继续留在主线上。
- 已完成分支默认隐藏，可手动显示。
- 最新节点显示标题，其他节点按需显示信息。
- 转折点拥有独立标识。

### 6.3 L3：详情

L3 不作为第四个固定页面。点击概要条目、Plan 条目、议题、认知修改或历史节点后，进入统一详情：

- 完整内容与状态。
- 关联项目、工作线和对象。
- 形成过程与变化结果。
- 原始对话气泡历史。
- 证据、交付与验证状态。
- 当前允许执行的操作。

## 7. 全局 Agent 对话

右下角悬浮按钮在 L1、L2、L3 始终存在。点击后打开右侧 Sidebar。

可选接收方：

- 各项目 Project Owner。
- Persona Collaborator。
- Workstate 全局协调 Agent。

默认接收方：

- 位于 L2 或 L3 时，默认选择当前项目 Owner。
- 位于 L1 时，默认选择上一次对话的接收方。
- 用户可以在发送前随时手动切换。
- 系统识别出明确的其他项目时可以切换，但必须显示接收方并允许撤回或改选。

会话历史先按接收方或项目分类，再显示该项目内的多个会话。Project Owner 的长期认知属于项目；用户可见会话只是不同讨论线，不产生新的 Owner 身份。

跨项目比较、项目优先顺序和全局工作安排由 Workstate 全局协调 Agent 处理。协作习惯、Persona 和 Loop 由 Persona Collaborator 处理。

## 8. 状态栏

状态栏退回快速查看和切换，不再承载完整项目界面。原来的“工作概要”和“会话状态”合并为一条项目动态流。

每个项目最多显示一个最新条目：

- 项目存在进行中的 Coder 会话时，显示会话状态。
- 项目当前没有进行中的会话时，显示最近一次工作概要。

所有条目按更新时间排序，只显示“本日”和“上一个有工作记录的日期”两个分组；更早内容进入完整 App 查看。点击条目返回对应 Coder 会话或项目页面。服务状态、设置和退出作为次要菜单项存在。

## 9. Agent 与数据职责

### Portfolio Router

- 判断新增会话内容属于哪个项目。
- 区分无项目后果、待继续讨论和可正式写入的内容。
- 不理解项目内部任务，不修改项目状态。
- 使用干净绑定和项目信息；错误绑定不得继续污染 Owner。

### Project Owner

- 持续维护一个项目的工作线、议题和项目工作概要。
- 使用同一项目的持久 Session 保持连续理解。
- 对长期认知变化只提出待确认修改。
- 不替用户决定产品方向、优先级和取舍。

### Workstate 全局协调 Agent

- 处理跨项目问题和总体工作安排。
- 汇总已有项目概要，不重新解释或改写各项目认知。

### Persona Collaborator

- 维护 Persona、协作规则和 Loop。
- 用户明确提出的规则可以直接形成修改。
- Agent 推断只能成为候选，必须经过用户确认。

## 10. 上下文交接

任何 Coder 接手项目前，Workstate 生成即时 Context Contract，包含：

- 正式项目认知。
- 当前项目工作概要。
- 当前工作线、议题和待确认内容。
- 与本次接手有关的协作规则。
- 关键历史与原始证据索引。

上下文在接手时生成，不因每轮会话重复重写。

## 11. 非目标

- 当前阶段不开发手机端。
- 不复制保存完整原始会话；只保存定位、索引和必要摘录。
- 不让工作概要替代项目认知或工作历史。
- 不让模型自动确认产品方向和长期认知修改。
- 不在状态栏继续堆叠完整项目功能。
- 不按固定对话轮数或自然日机械切分工作状态。

## 12. 成功标准

- 项目静默后，用户只阅读一份工作概要即可继续工作。
- 用户可以明确区分长期认知、项目工作概要、项目议题和工作历史。
- 任一结论可以回到顺序正确、可阅读的原始对话。
- 任何 Agent 获得 Context Contract 后可以继续当前项目，无需用户重新解释。
- Project Owner、Persona Collaborator 和全局协调 Agent 的当前接收方始终可见。
- 状态栏能够帮助用户发现需要注意的概要和会话，并快速返回对应工作窗口。
- 完整 App 在项目数量、历史长度和认知文档增长后仍保持清晰可读。

## 13. 已确认与待确认

### 已确认

- 完整 macOS App 成为主要承载，状态栏只保留合并后的项目动态流。
- 保留 L1、L2、L3 三层结构。
- L2 固定为看板、项目认知、工作历史三个页面。
- 项目认知在新客户端中采用块式文档编辑器。
- 工作概要与短期 Plan 合并，并统一为“已完成、正在进行、待处理”三个状态。
- 待办、待确认修改和等待验证事项进入对应状态。
- 议题属于项目，并与执行计划分离。
- 工作概要合集位于 L1 左下角，通过左侧 Sidebar 展示。
- 全局 Agent 对话位于右下角，通过右侧 Sidebar 展示。
- Persona Collaborator 可以从全局 Agent 对话直接访问。
- 原始对话采用最旧在上、最新在下的聊天气泡历史。

### 初始实现参数

- 项目连续 2 小时没有新动作后生成工作概要。

该时间是第一版触发参数，真实使用后可以依据生成频率和重新接手效果调整，不改变产品信息结构。
